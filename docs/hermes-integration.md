# Hermes Integration

How LibraVDB fits into the Hermes Agent platform: what we support, what we ignore, and how session identity flows across the platform.

---

## Session-Key Behavior Across Hermes Entry Points

LibraVDB uses `session_id` and `session_key` to scope memory ingestion, search, and compaction. Hermes provides these values differently depending on the entry point.

### CLI (`cli.py`)

| Property | Value |
|---|---|
| Session start | `on_session_start` hook fires with new session ID |
| Session ID | Persists for the life of the interactive REPL |
| Session key | Same as session ID |
| Reset | `/new`, `/reset`, `/clear` trigger `on_session_reset` — new session ID, old session finalizes |
| Session end | `on_session_end` fires on REPL exit or `/exit` |

LibraVDB emits `session_start`, `session_finalize`, and `session_end` lifecycle hints to the daemon at each boundary. The daemon uses these to snapshot, archive, and garbage-collect session state.

### Gateway (Telegram, Discord, Slack, et al.)

| Property | Value |
|---|---|
| Session start | `on_session_start` fires on first message after idle expiry |
| Session ID | Derived from platform user ID + gateway routing |
| Session key | Stable per-user; persists across idle timeouts |
| Reset | `on_session_reset` fires on idle rotation — new session key, old session archived |
| Session end | `on_session_finalize` fires on idle expiry |

Gateway sessions survive many individual message exchanges. The daemon benefits from `on_session_reset` hints because it can archive the previous window and start a fresh indexing segment without losing the user's durable memory.

### Cron

| Property | Value |
|---|---|
| Session start | Fresh AIAgent, no history |
| Session ID | Generated per job run |
| Session key | Same as session ID |
| Identity | May lack a platform user ID — namespace falls back to `agent-id:...` or `session-key:...` |

For cron jobs, the `resolve_durable_namespace` function (in `scopes.py`) handles the missing `userId` gracefully by walking the priority chain: explicit userId → session-key prefix → agent-id prefix → fallback → `"default"`.

### ACP (IDE Integration)

| Property | Value |
|---|---|
| Session start | `on_session_start` fires when editor connects |
| Session ID | Generated by ACP adapter on connection |
| Session key | Same as session ID |
| Reset | Editor disconnect/reconnect triggers new session |
| Session end | `on_session_end` fires on disconnect |

ACP sessions behave like CLI sessions from LibraVDB's perspective — the lifecycle hooks fire identically.

### Background / Subagent

| Property | Value |
|---|---|
| Session start | Child agent spawned by `delegate_task` |
| Session ID | Generated per delegation |
| Writes enabled | Only if `agent_context == "primary"` |
| Delegation hook | `on_delegation` fires with task + result after child completes |
| Memory tool | Blocked for all subagents — `on_memory_write` never fires from children |
| Context isolation | Subagents start with zero knowledge of parent conversation; only `goal` and `context` fields carry information |

LibraVDB skips writes in non-primary agent contexts to avoid duplicating memory. Delegation results are persisted via `on_delegation` so the parent session can recall subagent findings. The `memory` tool is one of five tools always blocked for subagents (alongside `clarify`, `code_execution`, `delegate_task` for leaf agents, and `send_message`), so curated memory mirroring only ever originates from the parent agent.

## What LibraVDB Supports in Hermes

| Hermes Feature | LibraVDB Stance | Details |
|---|---|---|
| **Memory provider** | Full implementation | All required + optional MemoryProvider methods |
| **Context engine** | Full implementation | Registered via `ctx.register_context_engine("libravdb", ...)` |
| **Lifecycle hooks** | Full coverage | `on_session_start`, `on_session_end`, `on_session_finalize`, `on_session_reset` |
| **Profile isolation** | Full support | `hermes_home` from `initialize()` — no hardcoded paths |
| **Built-in memory mirroring** | Supported | `on_memory_write` mirrors MEMORY.md/USER.md writes to LibraVDB |
| **Subagent delegation** | Supported | `on_delegation` emits lifecycle hints and ingests delegation results |
| **Context compression** | Supported | `on_pre_compress` persists key context before Hermes compresses |
| **Background prefetch** | Supported | `queue_prefetch` runs background searches to warm daemon caches |
| **Cross-session recall** | Supported | Config-gated via `crossSessionRecall` — searches user + global collections |
| **Exact recall** | Supported | Structured marker, identifier, and quoted-phrase extraction with token budget |
| **Predictive context** | Supported | Cached from `afterTurn` RPC responses, injected in next `assemble` |
| **CLI commands** | Full | `status`, `health`, `search`, `flush`, `export`, `journal`, `index`, `dream-promote`, `markdown-ingest` |
| **Config** | 60+ keys | All daemon tuning params exposed via `libravdb.json` |
| **TLS/mTLS** | Supported | Unix socket, loopback TCP, and secure TLS with client certificates |

## What LibraVDB Ignores (No Intersection)

| Hermes Feature | Reason |
|---|---|
| MCP integration | External tool protocol — no memory provider intersection |
| Provider routing / fallbacks | LLM-level concern — doesn't touch memory layer |
| Checkpoints / rollback | Filesystem snapshots — no intersection |
| Voice / vision / media | Media I/O — not a memory concern |
| Skills system | Prompt injection — doesn't touch memory provider |
| Prompt caching | Anthropic API feature — daemon-owned, not plugin concern |
| Context files (`.hermes.md`, etc.) | Hermes auto-discovers and injects these — daemon indexes what it receives |
| `@` references | Hermes expands before agent loop — plugin sees resolved text only |
| Skin / themes | CLI presentation — no intersection |
| Gateway platform adapters | Handled entirely by Hermes gateway layer |
| Cron scheduling | Hermes scheduler owns timing — plugin only handles the resulting sessions |

## Profile Isolation with HERMES_HOME

Hermes supports multiple profiles, each with independent configuration, memory, and session state. LibraVDB respects this isolation.

### How It Works

```
~/.hermes/                    ← default profile (HERMES_HOME not set)
~/.hermes.coder/              ← "coder" profile (HERMES_HOME=~/.hermes.coder)
~/.hermes.work/               ← "work" profile (HERMES_HOME=~/.hermes.work)
```

Each profile directory contains:
```
<HERMES_HOME>/
├── config.yaml               ← memory.provider: "libravdb"
├── libravdb.json             ← plugin config (60+ keys)
├── .env                      ← LIBRAVDB_AUTH_SECRET (if set)
└── sessions/                 ← Hermes session DB (Hermes-owned)
```

### Config Isolation

`initialize()` receives `hermes_home` in kwargs. The provider reads and writes config relative to this path:

```python
def _load_config(self) -> Dict[str, Any]:
    config_path = self._hermes_home / "libravdb.json"
    ...
```

Never hardcode `~/.hermes` — always use the `hermes_home` value from `initialize()`.

### Daemon Sharing

Multiple profiles can share one `libravdbd` daemon. The `userId` in each profile's `libravdb.json` scopes durable memory correctly:

```
Profile "default"  →  userId: "alice"  →  user:alice collection
Profile "work"     →  userId: "alice-work"  →  user:alice-work collection
```

Sessions are always scoped by session ID regardless of profile, so ephemeral turn data never leaks between profiles even when sharing a daemon.

### Concurrent Profiles

Hermes supports running multiple profiles concurrently (e.g., CLI in one terminal, gateway in another). Each profile gets its own `MemoryManager` → `LibraVDBMemoryProvider` instance with an independent gRPC channel. The daemon handles concurrent RPCs via its own thread pool.
